# Безопасность NOIR

## 1. Аудит прототипа (что было небезопасно)

Первая версия сайта работала целиком в браузере. Для реальных денег это было неприемлемо:

| # | Проблема | Риск | Как исправлено |
|---|----------|------|----------------|
| 1 | Баланс хранился в `localStorage` | Любой игрок мог «нарисовать» себе любую сумму через консоль браузера | Баланс хранится только в PostgreSQL. Каждое движение денег — строка в журнале `ledger` |
| 2 | Генератор исходов работал в браузере | Можно было подменить функцию и всегда выигрывать | Исходы считаются на сервере (HMAC-SHA256 от секретного сида). Клиент только показывает результат |
| 3 | В Crash точка краша была известна браузеру | Бот мог забирать выигрыш ровно перед крашем | Точка краша хранится только на сервере. Момент вывода определяется по часам сервера |
| 4 | В Минах позиции мин были в памяти браузера | Можно было открыть только безопасные клетки | Позиции хранятся на сервере и раскрываются только после окончания раунда |
| 5 | Не было аутентификации | Нельзя было отличить игроков, вывести деньги, вести историю | Регистрация, вход, серверные сессии, блокировка после 5 неверных паролей |
| 6 | Платёж «проходил» по нажатию кнопки | Бесплатное пополнение | Деньги зачисляются только по подписанному вебхуку провайдера (HMAC + окно 5 минут против повторов) |
| 7 | Inline-скрипты | Делали невозможным строгий CSP | JS вынесен в файлы, CSP `script-src 'self'` |

## 2. Что реализовано

**Деньги**
- Суммы — целые числа в тиынах (`BIGINT`), без ошибок округления float.
- Каждая операция: блокировка строки счёта (`SELECT … FOR UPDATE`) → проверка `balance >= 0` (и constraint в БД) → запись в журнал.
- Журнал `ledger` и `audit_log` — **append-only**: триггеры в БД запрещают `UPDATE`, `DELETE`, `TRUNCATE` даже приложению.
- Ключи идемпотентности: повторный вебхук, двойной клик или повтор запроса не зачислят деньги дважды.
- Сверка при каждом открытии дашборда: баланс каждого счёта = сумма его операций (виджет «Целостность журнала»).
- Выплаты округляются только вниз (в пользу оператора), лимиты на ставку и выигрыш.

**Аутентификация и сессии**
- Пароли: argon2id (параметры OWASP). Защита от перебора: 5 попыток → блокировка на 15 минут, rate limit 10 запросов в минуту на IP.
- Сессии серверные. В cookie — случайный токен, в БД — только его SHA-256. Cookie `HttpOnly`, `Secure`, `SameSite=Strict`, префикс `__Host-`.
- CSRF: токен сессии в заголовке `X-CSRF-Token` для каждого изменяющего запроса; для входа и регистрации — обязательный кастомный заголовок (блокирует кросс-доменные формы).
- Смена пароля завершает все остальные сессии.

**Персональные данные**
- E-mail, телефон, дата рождения зашифрованы AES-256-GCM (ключ `PII_KEY` вне БД). Утечка дампа БД не раскрывает контакты.
- Поиск по e-mail/телефону — через HMAC (`LOOKUP_KEY`), без расшифровки всей таблицы.
- В бэк-офисе роль «Наблюдатель» видит контакты в маске, без даты рождения и IP. Каждый просмотр карточки игрока пишется в аудит.

**Бэк-офис**
- Отдельные сессии сотрудников, **обязательная 2FA (TOTP)**, блокировка после 5 ошибок на 30 минут.
- Роли: администратор, финансы, риск/AML, поддержка, трейдер, наблюдатель. Права проверяются на сервере для каждого запроса.
- Ограничение доступа по IP (`ADMIN_IP_ALLOWLIST`) — рекомендуется открывать бэк-офис только из офиса или VPN.
- Каждое действие (вход, просмотр игрока, блокировка, корректировка баланса, одобрение вывода, расчёт события) — в неизменяемом журнале аудита.

**HTTP**
- Заголовки: CSP без inline-скриптов, HSTS (preload), `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, строгий Referrer-Policy.
- Rate limit: 300 запросов в минуту на IP глобально, 120 ставок в минуту, 10 входов в минуту, 5 входов сотрудников в минуту.
- Валидация каждого запроса (zod), лимит тела 64 КБ, все SQL-запросы параметризованы.
- Логи без cookie, токенов и CSRF (redact).
- Гео-блокировка по стране (`BLOCKED_COUNTRIES`, заголовок от CDN).

**AML / антифрод** — автоматические алерты для риск-отдела:
крупный депозит, крупный вывод, вывод без игрового оборота, более 5 депозитов за час, 3+ регистрации с одного IP за сутки, выигрыш ×500 и выше.
Перед выводом обязательны: KYC и оборот ставок не меньше суммы депозитов.

**Ответственная игра** — лимиты депозита (день/неделя/месяц), лимит проигрыша, напоминания о времени, самоисключение. Снижение лимита действует сразу, повышение — через 24 часа.

**Инфраструктура** (`docker-compose.yml`)
- БД в изолированной внутренней сети, недоступна из интернета.
- Контейнер приложения: не-root, read-only файловая система, `no-new-privileges`, все Linux capabilities сброшены.
- HTTPS автоматически (Caddy + Let's Encrypt), `/metrics` закрыт снаружи и защищён токеном.
- Ежедневные бэкапы БД. Grafana доступна только через SSH-туннель или VPN.

## 3. Тесты

`cd server && npm test` — 18 тестов, в том числе:
подделка CSRF, подделка подписи вебхука, повтор вебхука, ставка без денег, отказ несовершеннолетним, блокировка после перебора,
шифрование e-mail в БД, запрет изменения журнала, вход в бэк-офис без 2FA, запрет одобрения вывода для роли «Наблюдатель»,
воспроизводимость исходов Provably Fair, RTP всех игр.

## 4. Что ещё нужно сделать до запуска

Код не заменяет внешнюю проверку. Перед приёмом реальных денег:
1. **Пентест** у независимой компании (обычно 2–4 недели).
2. **Сертификация ГСЧ и математики игр** в аккредитованной лаборатории (GLI, iTech Labs, BMM, eCOGRA) — требование почти всех регуляторов.
3. **Хранение ключей** `PII_KEY`, `LOOKUP_KEY` и секретов вебхуков в KMS/Vault, а не в `.env`; план ротации ключей.
4. **WAF и защита от DDoS** (Cloudflare или аналог) перед сервером.
5. **Бэкапы вне сервера** (S3 с object lock) и регулярная проверка восстановления.
6. **Централизованные логи** (Loki/ELK) с хранением по требованию регулятора (обычно 5 лет).
7. **PCI DSS**: данные карт не должны попадать на ваш сервер — используйте только страницы оплаты провайдера (так и сделано).
8. **Bug bounty** после запуска.
